# Defining PoC Success Criteria (NFRs & KPIs)

## 1. "Works on My Machine" is Not a Success Criteria
A PoC is an experiment designed to answer a question. If the criteria for success are not defined *before* a single line of code is written, the PoC will suffer from scope creep and subjective evaluation ("I think it looks good").

## 2. The Hypothesis Format
Every PoC must start with a hypothesis.
- **Weak**: "We will build a new caching layer using Redis."
- **Strong**: "By implementing a Redis caching layer, we expect to reduce the P99 latency of the Product API from 800ms to 200ms, while supporting a throughput of 5,000 RPS on current hardware."

## 3. Defining Non-Functional Requirements (NFRs)
Global R&D cares about NFRs much more than the UI or business logic of a PoC. Your Success Criteria must explicitly measure these metrics:

### A. Performance & Scalability
- **Throughput**: Requests Per Second (RPS) the PoC can handle before dropping packets.
- **Latency**: P50, P90, and P99 latency. (Average latency is a deceptive metric; always measure percentiles).
- **Resource Utilization**: CPU and Memory consumption under peak load.

### B. Resilience & Fault Tolerance
- **Cold Start Time**: How long does the PoC take to recover after a crash?
- **Degradation**: If the database connection drops, does the PoC crash entirely, or does it serve stale cache data? (Graceful Degradation).

### C. Cost (FinOps)
- **Cost per User/Transaction**: If the PoC uses a massive distributed ML model, does the cloud compute cost exceed the revenue generated by the feature?

### D. Developer Experience (DX)
- **Onboarding Time**: How long does it take a new engineer on the Global team to spin up the Department's PoC locally? (If it requires 3 days of manual Docker configuration, it fails).

## 4. The PoC Exit Report
When the timebox (e.g., 4 weeks) expires, development stops. The team produces an Exit Report containing:
1. The Original Hypothesis.
2. The actual metrics measured against the Success Criteria.
3. The Recommendation: **Promote** (to MVP), **Pivot** (change technology), or **Kill** (abandon the idea). 

Killing a PoC that failed its success criteria is a massive victory, as it prevents the enterprise from sinking millions of dollars into an unscalable architecture.
