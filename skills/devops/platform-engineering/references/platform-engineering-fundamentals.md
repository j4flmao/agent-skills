# Platform Engineering Fundamentals: Concepts, Capabilities and First Steps

Platform engineering builds and runs an internal developer platform (IDP): a curated set of self-service capabilities that let stream-aligned teams build, deploy and operate software without needing deep expertise in every underlying tool. This reference defines the core concepts, the capability map, the minimum viable platform, and how to start and measure. Backstage configuration, golden paths, maturity models and team structures are covered in sibling references.

## Core Concepts

| Term | Meaning |
|------|---------|
| Internal Developer Platform (IDP) | The integrated set of tools, APIs, workflows and infrastructure offered to developers |
| Internal developer portal | The user interface to the platform (catalog, templates, docs), for example Backstage or Port; a portal is not the platform |
| Golden path (paved road) | An opinionated, supported way to do a common task end to end (create a service, add a database, deploy) |
| Self-service | Developers get capabilities on demand through APIs, templates or UI, without tickets |
| Platform as a product | The platform team treats developers as customers: research, roadmap, adoption metrics, support |
| Cognitive load | The mental effort teams spend on non-differentiating concerns; reducing it is the platform's purpose |
| Thinnest viable platform | The smallest set of capabilities that removes the biggest friction; may start as documentation and templates |

Team Topologies frames the platform team as providing services to stream-aligned teams through X-as-a-Service interaction, with enabling teams helping adoption.

## Why Platforms Exist

Symptoms that justify platform investment:
- Every team builds its own CI/CD, infrastructure modules and observability setup, with inconsistent security.
- Lead time for a new service or environment is measured in weeks and tickets.
- Developers spend significant time on infrastructure tasks unrelated to product work.
- Security and compliance controls are applied unevenly and audited manually.

Without these symptoms, a large platform effort is premature.

## Capability Map

| Capability | Typical implementation | Self-service interface |
|------------|------------------------|------------------------|
| Source and CI | GitHub/GitLab, reusable workflows | Repository templates, shared pipeline definitions |
| Delivery / deployment | Argo CD or Flux (GitOps), progressive delivery | Git commit, deployment manifests generated by templates |
| Runtime | Kubernetes clusters, serverless, PaaS | Namespaces/projects provisioned on request |
| Infrastructure resources | Terraform/OpenTofu modules, Crossplane compositions, cloud service catalog | Claims/requests (for example a `PostgresInstance` custom resource) |
| Environments | Ephemeral preview environments, standard dev/staging/prod | Created per pull request or on demand |
| Observability | OpenTelemetry, Prometheus, Grafana, logging stack | Automatic instrumentation and default dashboards per service |
| Security | Secrets management, image scanning, policy-as-code, identity | Built into templates and pipelines by default |
| Service catalog and docs | Backstage/Port catalog, TechDocs | Portal |
| Cost visibility | OpenCost, cloud cost tools | Per-service cost in the portal |

## Platform Architecture Layers

```text
Developer interfaces:   portal (Backstage/Port) | CLI | Git (YAML/IaC) | API
Platform orchestration: templates (scaffolder) | GitOps controllers | Crossplane / Terraform automation | workflow engine
Resource layer:         Kubernetes | cloud services (DBs, queues, buckets) | CI runners | observability backends
Governance:             identity & RBAC | policy-as-code (OPA/Kyverno) | audit | cost allocation
```

Interfaces are thin; capabilities live in the orchestration layer so they work from the portal, the CLI and Git alike.

## Minimum Viable Platform

Start with the highest-friction journey, usually "create and deploy a new service":

1. **Service template**: repository with application skeleton, Dockerfile, CI workflow, deployment manifests, health endpoints, OpenTelemetry setup.
2. **Pipeline**: shared, versioned CI workflow that builds, tests, scans and publishes an image.
3. **Deployment**: GitOps repository or Helm chart conventions; Argo CD/Flux deploys to a standard namespace.
4. **Observability defaults**: logs, metrics and traces wired automatically; a default dashboard and alert.
5. **Catalog entry**: ownership metadata (`catalog-info.yaml`) so the service is discoverable.
6. **Documentation**: one page explaining the golden path, and how to get help.

Measure time from "I need a new service" to "running in staging with monitoring" before and after.

## Interaction Model

| Channel | Use |
|---------|-----|
| Self-service (templates, APIs) | Default for common, well-understood needs |
| Office hours / chat channel | Questions and feedback |
| Enabling engagements | Platform engineers embed briefly with a team to adopt a capability |
| Requests / tickets | Rare cases not yet productized (and input to the roadmap) |

Golden paths are recommended, not mandated: teams may diverge if they accept owning the consequences (support, compliance evidence). Mandates without value reduce trust.

## Measuring the Platform

| Category | Metrics |
|----------|---------|
| Delivery performance (DORA) | Deployment frequency, lead time for changes, change failure rate, time to restore service |
| Developer experience | Survey-based satisfaction, perceived productivity, friction points (SPACE/DevEx frameworks) |
| Adoption | % of services on golden paths, template usage, active portal users |
| Efficiency | Time to first deploy for new services/new hires, tickets to platform team over time |
| Reliability of platform itself | Platform SLOs (CI availability, deploy success rate, provisioning time) |

Combine system metrics with regular developer surveys; numbers alone miss why something is painful.

## Build vs Buy

| Option | Consider when |
|--------|---------------|
| Open-source assembly (Backstage, Argo CD, Crossplane, Terraform) | Strong platform team, specific needs, desire for control |
| Commercial portals / platform orchestrators | Faster time to value, smaller team |
| Cloud provider PaaS (App Runner, Cloud Run, Azure Container Apps) | Simple workloads; the PaaS can be the platform |
| Hybrid | Buy the portal, build the golden paths |

The integration work (templates, policies, documentation, support) is the real cost regardless of choice.

## Common Pitfalls

| Pitfall | Better approach |
|---------|-----------------|
| Building a portal before having capabilities behind it | Start with templates and pipelines; add a portal when there is something to expose |
| Platform built without talking to developers | User research, pilots with friendly teams |
| Big-bang migration of all teams | Incremental adoption, starting with new services |
| Abstracting everything | Expose underlying tools where teams need flexibility; abstract only common cases |
| Platform team as a ticket queue | Productize repeated requests into self-service |
| No ownership metadata | Catalog with owners from day one |

## Checklist

- [ ] Developer pain points identified through interviews and data
- [ ] First golden path targets the highest-friction journey
- [ ] Self-service via templates/APIs; security and observability built in
- [ ] Service catalog with ownership for every service
- [ ] Platform roadmap and feedback channel published
- [ ] DORA, adoption and developer-experience metrics baselined
