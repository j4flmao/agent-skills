# Codebase Navigation Hints for Agents

Agents explore a repository with search and file reads under a context budget. Navigation hints are the signals that help them find the right file quickly: predictable naming, entry-point maps, ownership metadata, module boundary markers and searchable identifiers. This reference covers how to add those signals without writing documentation that rots.

## How Agents Navigate

Typical loop: read top-level instructions -> list directories -> grep/glob for identifiers -> read candidate files -> follow imports. Each step costs context. Hints work by:
- Making the first search hit the right place (unique, descriptive names).
- Reducing files read (index/map files, clear module boundaries).
- Preventing wrong edits (generated-file markers, ownership, "do not edit" notes).

## Predictable Structure

| Practice | Why it helps |
|----------|--------------|
| Feature-first directories (`src/orders/`, `src/billing/`) | One search term finds all related code |
| Consistent file suffixes (`*.controller.ts`, `*_test.go`, `*.spec.ts`) | Globs find all of a kind |
| Tests next to source or mirrored tree | Agent finds the test for a file deterministically |
| One public entry per module (`index.ts`, `__init__.py`, `mod.rs`) | Shows the module's API surface |
| Avoid generic names (`utils.ts`, `helpers.py`, `common/`) | Generic names produce many ambiguous hits |

## Entry-Point Map

Add a short map to AGENTS.md or a `docs/codemap.md` listing where flows start:

```markdown
## Code map
| Flow | Entry point | Key files |
|------|-------------|-----------|
| HTTP API | `src/main.ts` | `src/app.module.ts`, `src/*/**.controller.ts` |
| Order placement | `src/orders/place-order.usecase.ts` | `src/orders/order.entity.ts`, `src/payments/charge.ts` |
| Background jobs | `src/jobs/worker.ts` | `src/jobs/handlers/*.ts` |
| DB schema | `prisma/schema.prisma` | `prisma/migrations/` |
| Feature flags | `src/flags/flags.ts` | |
```

Keep it to entry points and stable files; do not enumerate every file. Validate in CI that listed paths exist.

## Searchable Identifiers

- Use full, domain-specific names: `calculateInvoiceTax` rather than `calc`.
- Keep the same term across layers (`Invoice` in DB table, entity, API, UI) or document the mapping once (glossary).
- Name constants and error codes uniquely (`ERR_ORDER_ALREADY_SHIPPED`) so a log message leads straight to the throw site.
- Avoid building identifiers dynamically (`handlers["on" + type]`) where possible; when unavoidable, add a comment listing the concrete names so grep finds them.

## Glossary

```markdown
## Glossary
| Term | Meaning | Code |
|------|---------|------|
| Account | Billing customer (company) | `Account`, table `accounts` |
| Member | User within an Account | `Member`, table `account_members` |
| Seat | Paid license for a Member | `Seat` |
```

Glossaries prevent agents from conflating similar concepts (user vs member vs account).

## Marking Generated and Vendored Code

- Generated files start with a header such as `// Code generated by <tool>. DO NOT EDIT.` (the Go convention `^// Code generated .* DO NOT EDIT\.$` is recognized by tooling).
- Mark them in `.gitattributes` with `linguist-generated=true` so review tools collapse them.
- State the regeneration command in the header and in AGENTS.md (`pnpm codegen`).
- Keep vendored or third-party code under clearly named directories (`vendor/`, `third_party/`) and list them as off-limits.

## Ownership Metadata

`CODEOWNERS` tells agents and reviewers who owns code and signals sensitive areas:

```
/src/payments/      @org/payments-team
/infra/terraform/   @org/platform
/src/auth/          @org/security
```

Agents can surface "this change touches a security-owned path; request review".

## Module Boundary Markers

- Per-directory README or `AGENTS.md` (nested files apply to their subtree in tools that support them) describing what belongs there and what must not be imported.
- Enforce boundaries with tooling (ESLint `no-restricted-imports`, `dependency-cruiser`, Go `internal/` packages, Python `import-linter`), so violations fail fast rather than relying on prose.

## Ignore Files to Reduce Noise

- `.gitignore` build outputs so they do not appear in searches.
- Tool-specific ignore files (e.g. `.cursorignore`, `.aiignore`, or settings that deny reading paths) for large fixtures, data dumps, lockfile-like artifacts, and secrets directories. Check which ignore files your agent tool honors.
- Keep large test fixtures in clearly named directories (`testdata/`, `fixtures/`).

## Comments That Help Navigation

```typescript
// Entry point for refund processing. Called from:
//  - RefundsController.create (API)
//  - jobs/handlers/chargeback.ts (webhook-driven)
// Side effects: writes refunds table, publishes `refund.created`.
export async function processRefund(cmd: RefundCommand) { /* ... */ }
```

Use such comments at entry points and seams, not everywhere; stale call-site lists mislead, so keep them where the set of callers is stable.

## Anti-Patterns

- Deep inheritance or DI indirection with no map: agents cannot find the implementation of an interface. Mention binding locations (`OrderRepository -> PrismaOrderRepository in orders.module.ts`).
- Multiple copies of similar code (old and new implementations) without marking the deprecated one.
- Dead code left in place; agents may extend it. Delete it or mark it clearly.
- Huge files (thousands of lines) that exceed comfortable read windows; split by responsibility.

## Checklist

- [ ] Feature-first layout with consistent suffixes
- [ ] Code map of entry points, path-checked in CI
- [ ] Glossary for overloaded domain terms
- [ ] Generated/vendored code marked with headers and `.gitattributes`
- [ ] CODEOWNERS for sensitive areas
- [ ] Import boundaries enforced by lint rules
- [ ] Noise excluded via ignore files
- [ ] Deprecated code marked or removed
