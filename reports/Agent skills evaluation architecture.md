# Agent Skills Evaluation Architecture

The eval suite for j4flmao/skills should have **four layers, ordered from cheapest to most expensive**. Layer 0 is static linting and offline routing checks, run for free on every PR. Layer 1 is a live trigger eval, sampled by clusters of easily confused skills. Layer 2 is a task-quality eval in paired A/B style: no-skill, old-skill, new-skill. Layer 3 is factuality verification for the roughly 3,900 reference files. The most important finding is that **routing, not content, is the number-one risk**. Claude Code reserves only about **1% of the context window** for the skill listing and drops descriptions when the budget is exceeded ([Claude Code skills docs](https://code.claude.com/docs/en/skills)), while the repo's 641 descriptions total about 319K characters (measured directly on the repo). Independent research also shows that a good skill that is never invoked is useless: in Vercel's experiment, skills in default mode **were not activated in 56% of cases**, and the pass rate matched the 53% baseline exactly ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). On quality, curated skills raise scores by only **+4.5pp on average in software engineering**, and **19% of tasks lose points** when a skill is present ([SkillsBench](https://arxiv.org/html/2602.12670v1)). The repo therefore needs paired statistics, a non-inferiority gate, and a reported rate of harmful skills, rather than a single average accuracy number. The recommended tool is `claude plugin eval` for the CI gate. promptfoo can be used instead, but only one of the two should be chosen as the primary format. Inspect AI + `inspect_swe` is for nightly sandboxed runs. Linting, statistical recomputation, and factuality should be custom-built in Node/uv.

## The listing budget makes routing the top risk

The repo currently routes with a keyword table in `.claude/rules/routing.md` plus `master-orchestrator`, not with the native skill auto-discovery mechanism. **Two separate systems** therefore need to be evaluated. The first is the keyword router, which is deterministic and so can be tested fully offline. The second is the description-based trigger mechanism, which applies when skills are installed as a plugin. The offline layer already has a concrete bug. A quick check of 16 routing targets in `routing.md` found that **15 targets have no corresponding `SKILL.md`**, for example `backend/universal/saga-patterns`, `security/zero-trust`, `planning/solution-architecture`, `data/data-etl-pipeline`, `devops/crossplane`. This kind of "dangling route" test is the cheapest there is and should be the first test in Layer 0.

For native triggering, physical constraints drive the eval design. Each skill costs about **100 tokens of metadata that always sit in context**, descriptions are limited to 1,024 characters ([Anthropic Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)), and Claude Code drops the descriptions of the least-invoked skills when the listing exceeds its budget ([Claude Code skills docs](https://code.claude.com/docs/en/skills)). By this estimate, 641 skills produce about **64K fixed tokens per turn**, so most skills will be routed by name alone. The methodological consequence is that the eval must run under the real listing configuration: all 641 skills installed with the real budget. It must not inject just one skill's description, as the skill-creator loop currently does. The uncertainty should also be stated plainly: the documentation does not say whether the budget is measured in characters or tokens. In addition, there is a community report (secondary source) that heavy configurations, with more than 40 skills plus MCP, keep skills from triggering in `-p` mode ([claudeissues #34648](https://claudeissues.com/issue/34648-skills-never-trigger-in-p-mode-with-heavy-config-40-skills-mcp-servers)).

The literature on tool selection supports a **two-stage routing approach: retrieve first, then select**. Anthropic's Tool Search Tool raised accuracy on an MCP eval from **49% to 74% (Opus 4)** and from **79.5% to 88.1% (Opus 4.5)**, while cutting tokens by about 85% ([Anthropic engineering](https://www.anthropic.com/engineering/advanced-tool-use)). RAG-MCP reports an increase from 13.62% to 43.13% ([arXiv 2505.03275](https://arxiv.org/html/2505.03275v1)). MetaTool shows that LLMs are weakest at two things: choosing among similar tools, and answering "None" when no tool fits ([MetaTool](https://arxiv.org/html/2310.03128v5)). The eval should therefore separate two numbers. The first is the **retriever's recall@k**, i.e. whether the correct skill is in the top-k. The second is the **model's conditional accuracy**, i.e. whether the model picks the correct skill once it is already in the candidate list. End-to-end accuracy is approximately the product of the two, and the split tells you whether to fix names/the index (stage 1) or the descriptions (stage 2).

### The trigger dataset must trap skills with overlapping names

The official recipe for a single skill is about **20 queries, with 8–10 should-trigger and 8–10 near-miss**. Each query runs 3 times with a trigger-rate threshold of 0.5, a stratified 60/40 train/test split, at most 5 iterations, and the description is chosen by test score ([skill-creator](https://raw.githubusercontent.com/anthropics/skills/main/skills/skill-creator/SKILL.md); [agentskills.io](https://agentskills.io/skill-creation/optimizing-descriptions)). agentskills.io warns against stuffing keywords from failed queries into the description, because that is overfitting. Multiplying this recipe by 641 skills yields about 38K `claude -p` calls per pass, so tiering is needed. T1 covers all 641 skills with 3–5 positives each, about 2–3K prompts in total. T2 targets easily confused clusters: 8–10 positives per member, and each skill's positives serve as negatives for the other skills in the cluster. T3 applies the full 20-query recipe to important skills. Finally, a shared NONE set of about 100–200 prompts should trigger no skill at all. The repo already has clusters that belong in T2. For example, three `chaos-engineering` skills live in `devops/`, `site-reliability-engineering/`, and `quality-assurance/`. Four `gitops` variants are scattered across `devops/` and `cloud-native/`. There are also the pairs `data/etl-pipeline` vs. `data/etl-pipelines`, and `ml/feature-store` vs. `data/feature-store`.

Keyword leakage is a trap specific to this repo. The repo's descriptions spell out the sentence "Use this skill when the user says 'X'" verbatim, so any prompt that repeats that keyword will inflate the score. The control has three steps. First, generate prompts from task scenarios, not from descriptions. Second, ban the skill name and trigger keywords in at least 50% of positives. Third, report accuracy per BM25/n-gram overlap bucket between prompt and description, and treat accuracy in the low-overlap bucket as the honest number. Use a model from a different family to generate the synthetic data, then have humans review 10–20%. This is exactly the "generate with an LLM, fix with humans" process skill-creator uses with `eval_review.html`.

| Routing metric | Definition | Notes |
|---|---|---|
| Precision / recall / F1 per skill | Multi-class classification over 641 skills + a NONE class | Report both macro and micro |
| Top-1, top-3/5, MRR | Computed for the keyword router and the BM25/embedding retriever | Offline, free |
| False-trigger rate | Share of prompts in the NONE set that trigger any skill | Analogous to BFCL's irrelevance detection |
| Within-cluster confusion matrix | C[A→B]; flag when > 10–20% or when asymmetric | Computed only within T2 clusters |
| Flaky prompt rate | Trigger rate in the interval (0, 1) after ≥ 3 runs | Measures stability |
| Accuracy by overlap bucket | The low-overlap bucket is the headline number | Guards against keyword leakage |

Offline proxies such as embedding cosine, BM25, and Jaccard are cheap enough to run over all 641×641 pairs. They are for finding easily confused clusters, but **they do not replace live tests**. The reason is that real triggering also depends on descriptions being truncated and on Claude skipping skills for single-step tasks. In addition, ToolRet shows that conventional IR retrievers perform poorly on tool retrieval ([ToolRet](https://aitopics.org/doc/arxivorg:DCB3A6F3)). No published study has measured the correlation between embedding similarity and the live confusion rate. The repo should measure the Spearman correlation between the two itself before trusting the proxy.

## A skill is only worth something when it beats a paired baseline

The standard design runs the same prompt set across different arms. New skill vs. no skill. Edited skill vs. the `old_skill` snapshot from before the edit ([skill-creator](https://raw.githubusercontent.com/anthropics/skills/main/skills/skill-creator/SKILL.md)). `claude plugin eval` does the WITH/W/OUT ablation out of the box and reports Δ. In two-arm mode, the `tool_used: Skill` grader is excluded from scoring so it does not inflate Δ ([plugin evals](https://code.claude.com/docs/en/plugin-evals)). For this repo, two more arms should be added. A **forced-load** arm force-loads the skill into context, to separate content quality from trigger quality: the lesson from Vercel is that 53% = 53% does not prove the content is bad. A **length-matched control** arm uses an unrelated document of equivalent token length, because SkillsBench itself admits it has not ruled out a "just more context" effect ([SkillsBench](https://arxiv.org/html/2602.12670v1)).

Graders should prefer scoring the final state of the environment, not the agent's self-description and not a rigid step-by-step check ([Anthropic: Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). For example, for the task "write a Helm chart", the grader uses `helm lint`, `helm template | kubeconform -strict`, and a policy check. For "design an idempotent payment API", the grader uses spectral lint on the OpenAPI spec, asserts that POST carries an `Idempotency-Key` header, and, if the agent writes code, sends the POST twice and checks that only one charge occurs. For "security PR review", plant real vulnerabilities and decoy vulnerabilities, then score recall on the real ones and false positives on the decoys. Each SKILL.md has its own "Response Format" section, so **format compliance must be scored separately from correctness**, so that format does not mask quality. Use LLM-as-judge only for qualities that cannot be mechanized. When using a judge, each rubric item is a concrete PASS/FAIL, each dimension gets its own judge, an "Unknown" option is available, and the judge is calibrated against human labels ([Anthropic evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). For pairwise comparisons, swap the positions of the two outputs, because position bias is systematic ([arXiv 2406.07791](https://arxiv.org/html/2406.07791v1)). Use a judge from a different model family to reduce self-preference ([arXiv 2410.21819](https://arxiv.org/pdf/2410.21819)). The plugin eval documentation further advises: if the Skill fired and Δ is negative, suspect the judge before suspecting the skill ([plugin evals](https://code.claude.com/docs/en/plugin-evals)).

### Per-skill suite sizes are only enough to catch large effects

The headline number should be pass@1, i.e. the average success rate. Add **pass^k** for skills meant to make behavior consistent: 75% per run drops to only about 42% pass^3 ([Anthropic evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Statistically, compute the paired Δ per task, average over K runs, then compute the standard error clustered by task family. The reason is that the clustered SE can be **more than three times the naive SE**. Pairing reduces variance almost for free, because scores on the same question across two arms correlate at about 0.3–0.7 ([Miller, arXiv 2411.00640](https://arxiv.org/html/2411.00640v1); [Anthropic research](https://www.anthropic.com/research/statistical-approach-to-model-evals)). In Miller's example, detecting a 3pp difference at 80% power requires about **969 questions**. Applying the same formula with illustrative variance assumptions (ω²≈0.1, σ²≈0.2, K=5), 10 tasks per skill only detect an effect of about 38pp, 20 tasks about 27pp, 40 tasks about 19pp. These are illustrative numbers; a pilot run is needed to estimate the real variance. The practical conclusion is that **adding tasks reduces SE faster than adding runs**, and K beyond about 5 adds little. The CI gate for each skill edit should be set as **non-inferiority**: block the merge if the lower bound of the 95% CI of Δ is below −10pp. It should not require proving a significant improvement. Small effects, such as +4.5pp in SWE, can only be estimated at the aggregate level: use the hierarchical model `Δ ~ 1 + (1|category) + (1|skill) + (1|task)` on a stratified sample, with the `errorbars` package available for clustered and paired SE ([PyPI errorbars](https://pypi.org/project/errorbars/)).

The single most important health metric for the library is **the share of skills with a statistically significant negative Δ**. There are three reasons. SkillsBench found 16/84 tasks losing points, with one task dropping as much as −39.3pp. "Comprehensive"-style skills reduced results by −2.9pp. And loading 4 or more skills yields only +5.9pp versus about +18pp when loading 1–3 skills ([SkillsBench](https://arxiv.org/html/2602.12670v1)). Notably, the SkillsBench paper contradicts itself on its headline number: the abstract says +16.2pp, the Fig. 2 caption says +12.66pp. These numbers should therefore be cited only as directional evidence. Normalized gain should only be reported alongside absolute Δ, because 90→95% and 10→55% give the same g=0.5.

## Reference docs need verification on a cost ladder

No single tool can check the factuality of an entire corpus of technical documentation, so a multi-stage pipeline is needed. The first stage is deterministic checks: lychee for links, with a `.lycheecache` cache and 429/5xx status codes excluded from the cache ([lychee](https://lychee.cli.rs/github_action_recipes/caching)). Next, extract code blocks by language tag and run the native validators: `kubeconform -strict` ([kubeconform](https://github.com/yannh/kubeconform)), Pluto `--target-versions` with exit code 2 for deprecated APIs and 3 for removed APIs ([Pluto](https://pkg.go.dev/github.com/fairwindsops/pluto/v3)), actionlint ([actionlint](https://github.com/rhysd/actionlint)), shellcheck, hadolint, tflint. Add a YAML file of deprecated-pattern regexes taken from Kubernetes's official guide: `batch/v1beta1` CronJob, `PodSecurityPolicy` removed in 1.25, `autoscaling/v2beta2` removed in 1.26 ([Kubernetes deprecation guide](https://kubernetes.io/docs/reference/using-api/deprecation-guide/)). Snippets in docs are often just code fragments, so they must be labeled "unvalidatable", separately from "invalid".

The second stage targets the most common error in LLM-written text: **package names that do not exist**. Commercial models hallucinate package names in about 5.2% of samples on average, open-source models in about 21.7% ([Socket](https://socket.dev/blog/slopsquatting-how-ai-hallucinations-are-fueling-a-new-class-of-supply-chain-attacks)). A 2026 replication found 127 identical hallucinated package names across all five frontier models ([arXiv 2605.17062](https://arxiv.org/pdf/2605.17062)). Every package name mentioned in the docs should therefore be looked up on npm, PyPI, crates.io, and Maven to check whether it exists, its latest version, and whether it is deprecated or yanked. The registries' endpoint details were not verified in this research. Verification effort should concentrate on niche skills. The reason is that GPT-4o calls only **38.58% of low-frequency APIs** correctly ([CloudAPIBench, Amazon Science](https://www.amazon.science/publications/on-mitigating-code-llm-hallucinations-with-api-documentation)), and enterprise models reach only 48–51% on version-specific API tasks ([GitChameleon 2.0](https://sotaverified.org/papers/250712367)).

The final stage uses an LLM to split text into atomic claims and check them against official documentation on an allow-listed set of domains, following the FActScore/SAFE pattern. This stage applies only to prose claims that the previous two stages cannot check. Automated judges have limited reliability: SAFE agrees with crowd workers only 72% of the time ([DeepMind](https://deepmind.google/research/publications/85420/)). FActScore's estimate errs by less than 2% at the aggregate level, but has only been validated on biographies ([FActScore](https://arxiv.org/abs/2305.14251)). To get a corpus-wide number with a valid confidence interval, have the judge label every claim, have humans label about 300–500 claims from a stratified sample, then use **prediction-powered inference**. This method yields intervals that remain valid even when the judge is poor; the intervals are just wider ([arXiv 2405.06034](https://arxiv.org/pdf/2405.06034v1.pdf)). The `truescore` library provides correction for the judge's sensitivity and specificity ([truescore](https://pypi.org/project/truescore/0.7.1/)). Reported rates should use the Wilson interval instead of Wald. If no error is found in n samples, the 95% upper bound is approximately 3/n ([Rule of three](https://en.wikipedia.org/wiki/Rule_of_three_(statistics))). Each file should have `last_verified` and `verified_against` frontmatter, and CI flags stale files using a formula of age × volatility of the domain. No benchmark yet measures hallucination rates specifically for agent skill documentation corpora. The rates cited above were all measured on model-generated code.

## Every percentage point must come with a token price

Skill cost has three layers, and each must be measured separately. L1 is the listing or rules that always sit in context, paid every turn. L2 is the SKILL.md body when triggered, with a target under 5K tokens. L3 is the reference files actually `Read` during a task, which cost nothing until read ([Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)). For this repo, L1 is currently the `CLAUDE.md` + `rules/*.md` bundle loaded up front, including the very long `routing.md`. This must be counted with the token counting endpoint, noting that the 5.x model family produces about 30% more tokens for the same text ([token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting)), or with `/skill-doctor`. Prompt caching reduces L1's monetary cost to 0.05× base for Opus 5.5 and Sonnet 5.5 ([prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). However, caching does not reduce the context occupied or the attention dilution. It is also invalidated when the prefix changes, so the listing must not be generated with a timestamp.

Comparisons between variants (no-skill, current, trimmed version, reference-split version) should be presented as an **accuracy–cost Pareto plot with confidence intervals**. HAL shows that the most expensive model is rarely on the Pareto frontier, and that the scaffold strongly affects both accuracy and cost ([HAL](https://hal.cs.princeton.edu/)). In the other direction, Gemini Flash with skills beat Gemini Pro without skills at 44% lower cost per task ([EmergentMind summary](https://www.emergentmind.com/topics/skillsbench-benchmark)). The key metric is **cost-per-success = total $ / number of successful tasks**. Report partial credit alongside it, because pass rate alone is not enough ([NeurIPS 2026](https://neurips.cc/virtual/2026/175739)). Also report the number of tool calls, references read per task, and p50/p95 wall-clock time.

## Proposed architecture: two harnesses, one case format, four CI tiers

Choose a framework on one criterion: whether it can run real Claude Code with skills and measure Δ against a baseline. Only three tools can do this: `claude plugin eval`, promptfoo `anthropic:claude-agent-sdk`, and Inspect `inspect_swe.claude_code()`. DeepEval, Braintrust, and LangSmith only score traces you produce yourself. Ragas may have stopped development. OpenAI hosted Evals goes read-only on 10/31/2026 and **shuts down on 11/30/2026** ([Langfuse migration guide](https://langfuse.com/resources/engineering/migrate-from-openai-evals.md)).

`claude plugin eval` is the default choice for CI. It has a built-in baseline, 3 runs by default, 3-vote judging, `--max-cost-usd`, exit codes 0/1/2, and result JSON that records `claudeVersion` ([plugin evals](https://code.claude.com/docs/en/plugin-evals)). Its drawbacks are that it has no custom code-based graders, and it can be disabled server-side. promptfoo is a strong alternative, with a `skill-used` assertion, `max_budget_usd`, caching, and a GitHub Action that comments on PRs. However, promptfoo has been owned by OpenAI since March 2026, and its `skills` filter is not a sandbox ([promptfoo provider](https://www.promptfoo.dev/docs/providers/claude-agent-sdk/); [OpenAI](https://openai.com/he-IL/index/openai-to-acquire-promptfoo/)). Inspect + `inspect_swe` runs Claude Code in Docker with a pinned version, suitable for nightly runs that need real isolation ([inspect_swe](https://meridianlabs-ai.github.io/inspect_swe/claude_code.html)). The skill-creator and plugin eval case formats cannot read each other's files. So **pick one canonical format**, preferably the plugin eval format, and use a script to convert to the other. Because the 641 skills are not in `.claude/skills/`, every harness needs a scaffold step that copies the skill under test into the working dir. Two points are unverified: whether plugin eval accepts a directory of hundreds of skills as a single plugin, and how it scales at that size.

```
evals/
  harness/            # Node + uv: scaffold skills into .claude/skills/, read stats, PPI
  lint/               # dangling routes, frontmatter, ≤1024 characters, "Do NOT use for", duplicate names
  routing/
    clusters.json     # easily confused clusters from embedding×2 + BM25 + leaf-name collision
    triggers/<area>/<skill>.json   # {query, should_trigger, primary, acceptable[], overlap_bucket}
    none.json         # 100–200 prompts that must not trigger
    splits.lock       # fixed train/val split, keeping each paraphrase family intact
  tasks/<area>/<skill>/<case>/     # prompt.md, case.yaml (tags: tierA|B, skill, area), graders/, fixtures/, solution.sh
  factuality/
    deprecated-patterns.yaml
    claims/           # extracted claims table (file, line, type, value)
    human-labels/     # 300–500 claims labeled by 2 annotators, κ
  baselines/<model-id>/<claudeVersion>.json  # commit
  results/            # gitignore
```

| Group | Primary metrics (mean ± 95% CI) | Gate |
|---|---|---|
| Lint/static routing | Number of dangling routes, descriptions > 1,024 characters, duplicate names | Hard fail |
| Offline routing | Top-1/top-5, MRR, within-cluster confusion matrix | Must not regress vs. baseline |
| Live trigger | Precision/recall/F1, false-trigger on the NONE set, low-overlap-bucket accuracy, flaky rate | Advisory → hard for Tier A |
| Quality | pass@1, pass^3, Δ vs none/old, partial credit, format compliance, % of skills with negative Δ | Non-inferiority −10pp |
| Factuality | Hallucinated-entity rate, outdated rate, broken links, snippet pass rate (Wilson/PPI) | Hard fail on deprecated regexes |
| Performance | L1/L2/L3 tokens, cache read/write, cost-per-success, tool calls, p50/p95 | Warn on increase > X% |

The roadmap has four phases. **Phase 0 (weeks 1–2, $0)** extends `scripts/validate-agent-governance.js` to add the dangling-route test, the description length limit, deprecated regexes, lychee, and a `pr-static.yml` workflow. **Phase 1 (weeks 3–5)** builds the map of easily confused clusters and the T1/T2/NONE trigger sets, measures offline routing, then runs live triggering on the T2 clusters with a pinned model and the real listing. The results will decide whether to merge overlapping skills or rewrite descriptions. **Phase 2 (weeks 6–10)** selects about 50 Tier A skills by risk level, prioritizing security, payments, and destructive operations. Each skill gets 10–20 tasks with deterministic graders, K=5, three arms. Run a pilot to estimate the real variance, then enable `pr-evals.yml` to run only the edited skills, with `--ablation none`, a 0.8 threshold, and `--max-cost-usd`, disabled for PRs from forks and triggered by a label. **Phase 3 (from month 3)** runs `nightly-evals.yml` with full ablation and a judge from a different model family. Tier B is sampled at 10% per category on a rotating basis. The factuality pipeline runs with PPI, and all of Tier A is re-baselined whenever a new model ships.

## Conclusion

For a library of 641 skills, the question "is the skill good" comes after the question "is the skill found". Current evidence shows the skill count far exceeds the threshold at which models select tools reliably. The repo also has routing targets that do not exist. The highest-return investment is therefore **merging overlapping clusters and organizing routing hierarchically or around retrieval**, not polishing each SKILL.md. The eval suite should be designed to make that decision: merge, rewrite, or delete a skill.

The second consequence is that the repo should change its definition of "success". With a small average effect in software engineering and nearly 1/5 of tasks harmed by skills, the realistic goal is not to prove each skill helps. The goal is to **prove that no skill causes harm beyond the allowed threshold**, and to estimate benefit at the category level with a hierarchical model. Framing the goal this way is cheaper, more statistically honest, and turns the eval suite into a tool for pruning the library rather than just scoring it.
